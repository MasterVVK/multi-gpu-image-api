# multi-gpu-image-api

Один HTTP API для генерации изображений на нескольких GPU-узлах, с арбитражем
VRAM для карт, которыми вы владеете **не единолично**.

Заменяет набор отдельных FastAPI-сервисов, каждый из которых считал GPU своим.
У нас это были четыре сервиса на одной RTX 3090 — с предсказуемым результатом в
логах: `CUDA out of memory` и OOM-killer, уносивший соседние проекты.

Что добавляет:

* **арбитраж VRAM** — одна генерация на карту, ожидание свободной памяти по
  остаточному принципу, честный отказ вместо OOM;
* **сторож утечек** — память не остаётся занятой после сбоя, отмены или падения шлюза;
* один контракт вместо нескольких расходящихся;
* очередь и история задач переживают перезапуск (раньше жили в словаре процесса);
* аутентификация по ключу и закрытая дыра обхода пути в выдаче картинок;
* несколько GPU-узлов без правки кода;
* OpenAI-совместимый эндпоинт — готовые клиенты и UI работают как есть.

## Почему шлюз плюс воркеры, а не один процесс

Модели стоят на несовместимых стеках:

| бэкенд | torch | transformers | diffusers |
|---|---|---|---|
| Qwen-Image | 2.9.1 | 4.57.3 | 0.36.0 |
| Z-Image | 2.10.0 | **5.1.0** | 0.36.0 |
| ERNIE-Image | 2.5.1+cu121 | **5.5.4** | main @ `c8c8401` |
| HiDream-O1 | 2.5.1+cu121 | **4.57.1** (жёсткий пин) | не используется, вендорный код |

В один venv это не собирается. Поэтому «единый сервис» — это один публичный
процесс, который вообще не импортирует torch, плюс тонкие воркеры, каждый из
своего venv:

```
клиенты ──8010──▶ шлюз  (свой .venv, БЕЗ torch)
                  FastAPI + SQLite + арбитр VRAM + Prompt Enhancer
                        │ httpx                    │ httpx через ssh -L
              127.0.0.1:8101..8106          127.0.0.1:18101..18106
              ┌──────────────────┐          ┌──────────────────┐
              │ узел node-a      │          │ узел node-b      │
              │ 8101 qwen        │          │ 18101 qwen       │
              │ 8102 zimage      │          │ 18102 zimage     │
              │ 8103 ernie       │          │ 18104 hidream    │
              │ 8104 hidream     │          │ 18105 qwen21     │
              │ 8105 qwen21      │          │ 18106 moss       │
              │ 8106 moss        │          └──────────────────┘
              └──────────────────┘
```

Пакет воркера ставится в каждый чужой venv `.pth`-файлом, а не через pip.
`.pth` — это одна строка с путём: он структурно не способен сдвинуть чьи-либо
пины и снимается одной командой.

Воркер отдаёт готовый PNG байтами в HTTP-ответе, шлюз — единственный, кто пишет
на диск. Поэтому удалённый узел не требует общей файловой системы, а статус
`completed` означает ровно «файл у шлюза есть».

«Замер» — `scripts/measure_vram.py`, на дефолтном пресете, за вычетом фона от
соседей по карте, плюс 5%. Калибровка не формальность: у `qwen-image` цифра из
документации проекта (16 ГБ) оказалась **на 4.4 ГБ ниже** реального пика в
20.4 ГБ. На тесной карте этот зазор покупает вам OOM вместо честного отказа.

Qwen-Image 2.1 — преемник 2512 в отдельном бэкенде `qwen21` (свой venv: нужен
`QwenImage21Pipeline` из main-ветки diffusers и transformers ≥ 5.17). В 24 ГБ
рядом с соседями он уложен тремя решениями, все замерены на RTX 3090:

| текстовый энкодер | трансформер | пик VRAM | 2752×1536, 40 шагов |
|---|---|---|---|
| на карте | bf16 | 17.2 ГБ | 300–308 с |
| на CPU | bf16 | 16.8 ГБ | 290 с |
| на CPU | fp8 | **10.1 ГБ** | **277 с** |

* энкодер (17.5 ГБ) на карту не попадает: промпт кодируется на процессоре за 10–20 с
  (зависит от длины);
* веса трансформера хранятся в float8 и приводятся к bf16 послойно;
* VAE декодирует плитками 1024 px — целиком картинка 2K в 24 ГБ не декодируется вовсе.

У 2.1 CFG по умолчанию выключен (`guidance_scale=1.0`): `negative_prompt` действует
только при `guidance_scale > 1`, и это удваивает время. У Turbo шаги и guidance
зашиты в чекпойнт: другое число шагов и `negative_prompt` шлюз отвергает с 422.
Веса 2.1 распространяются по Qwen Research License (некоммерческое использование).

`qwen-image-2.1-bf16` — тот же чекпойнт с полными весами трансформера (вторая строка таблицы
выше): эталонное качество ценой 16.8 ГБ. На общей карте он запускается, только когда соседи
ушли, поэтому клиенту, которому результат важнее времени, стоит просить его первым и при
отказе `vram_unavailable` повторять запрос с `qwen-image-2.1`.

MOSS-Image (OpenMOSS, Apache-2.0) — бэкенд `moss` в том же venv, что и `qwen21`, но своим
процессом. Пайплайн у модели собственный (`pipeline_moss_image.py` в репозитории весов,
`trust_remote_code`), поэтому воркер работает с `HF_HUB_OFFLINE=1` и читает код из
зафиксированного снапшота. Энкодер так же вынесен на процессор. CFG включён при любом
`guidance_scale`, кроме 1.0; при 1.0 `negative_prompt` шлюз отвергает с 422.

Оба бэкенда требуют Python ≥ 3.11 (transformers ≥ 5.17) — на узле с системным 3.10 задайте
`PYTHON=` для `infra/remote-node/bootstrap.sh`.

Бэкенд ERNIE выбрасывает встроенный в пайплайн prompt-enhancer (Ministral-3.3B)
при загрузке. `use_pe=False` его не убирает: это *компонент* пайплайна, а не
ветка в `__call__`, поэтому он грузится всегда. Выброс снизил замеренный пик
с более чем 23.5 ГБ, на которых модель падала с OOM на 24-гигабайтной карте,
до 16.5 ГБ.

Живой каталог — `GET /api/v1/models`, определения — `worker/images_worker/registry.py`.

Добавить модель — это один `ModelSpec` и один класс бэкенда; шлюз, планировщик и
API править не нужно.

## Политика VRAM

Исходное допущение: карта **делится с задачами, которыми вы не управляете** — у
нас это ollama, RAG-стек, TTS и whisper. Отсюда правила:

1. **Эксклюзив.** На узле одновременно идёт одна генерация. Остальные ждут в очереди.
2. **Одна резидентная модель на узел.** Перед загрузкой другой предыдущая выгружается.
3. **Преflight по `nvidia-smi`**, никогда по `torch.cuda.memory_allocated()`: при
   `enable_model_cpu_offload()` torch показывает ~0 у загруженной модели, потому
   что веса лежат в системной RAM и приезжают на карту помодульно.
4. **Ждём до 10 минут.** Не хватает карты — задача уходит в `waiting_vram`, шлюз
   опрашивает все узлы каждые 5 секунд. Освободилось — выполняем. Истёк
   `IMG_VRAM_WAIT_TIMEOUT_S` — задача завершается с `error_code=vram_unavailable`
   и текстом, который называет, кто именно занял карту:

   ```
   не дождались свободной VRAM за 600 с — node-a: free 11781 МБ, резерв 1024 МБ,
   нужно 21500 МБ, ollama держит qwen3-embedding:8b (6.3 ГБ),
   NuExtract3-GGUF:Q4_K_M (3.9 ГБ), qwen2.5:0.5b (0.7 ГБ)
   ```

5. **Соседей не вытесняем.** Чужие задачи приоритетнее. Сервис умеет только
   ждать и отказываться.

Стоять в очереди за *нашей же* задачей — не нехватка VRAM: отсчёт десяти минут в
этом случае не идёт, иначе всё, что оказалось вторым в очереди, отваливалось бы.

### Чтобы память не зависала при сбоях

* выгрузка в `finally` на каждом пути выхода — успех, ошибка, таймаут, отмена;
* сторож раз в 30 с проверяет узлы без аренды: резидентная модель при простое
  выгружается; воркер, отвечающий «занят» без нашей аренды (сирота после падения
  шлюза), отменяется; память, удерживаемая дольше `IMG_STUCK_VRAM_SECONDS`,
  эскалируется до рестарта воркера;
* у воркера есть свой idle-unloader — страховка на случай, когда упал сам шлюз;
* `IMG_WORKER_IDLE_EXIT_SECONDS` завершает процесс после долгого простоя: только
  так отдаётся CUDA-контекст (~340 МБ на воркер);
* при старте шлюз выгружает всё на всех воркерах, прежде чем принимать задачи;
* каждое вмешательство пишется в таблицу `vram_incidents`, читается через
  `GET /api/v1/nodes/{name}/incidents`. Реальные записи из наших прогонов:
  `unload hidream-o1 — освобождено 16802 МБ`, `cancel_orphan`.

## API

### Нативный

```
POST   /api/v1/generate              {model, prompt, aspect_ratio|width+height, ...}
GET    /api/v1/tasks/{id}
GET    /api/v1/tasks/{id}/wait?timeout=300     ждать без цикла поллинга (макс. 1800)
DELETE /api/v1/tasks/{id}            отмена
GET    /api/v1/tasks?limit=&status=
GET    /api/v1/images/{path}         ?sig=... — подписанная ссылка, работает в <img>
GET    /api/v1/models
GET    /api/v1/resolutions?model=
GET    /api/v1/queue                 кто работает, кто ждёт и сколько осталось
GET    /api/v1/nodes                 GPU, резидентная модель, аренда
GET    /api/v1/pe/status             состояние цепочки Prompt Enhancer
GET    /healthz  /readyz             без ключа; /readyz отдаёт 503, если узлов нет
```

```bash
KEY=$(grep '^IMG_API_KEYS=' .env | cut -d= -f2- | cut -d, -f1)

TID=$(curl -sS -X POST localhost:8010/api/v1/generate -H "X-API-Key: $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"z-image-turbo","prompt":"a red cube on a white table","aspect_ratio":"1:1"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["task_id"])')

curl -sS "localhost:8010/api/v1/tasks/$TID/wait?timeout=600" -H "X-API-Key: $KEY"
```

### OpenAI-совместимый

```python
from openai import OpenAI
c = OpenAI(base_url="http://localhost:8010/v1", api_key=KEY)
r = c.images.generate(model="hidream-o1", prompt="blue whale over a city", size="2048x2048")
print(r.data[0].url)
```

Алиасы `gpt-image-1` / `dall-e-*` уходят в `IMG_OPENAI_DEFAULT_MODEL`; `quality` —
множитель шагов; `n` ограничен `IMG_OPENAI_MAX_N`, потому что при эксклюзивной
аренде четыре задачи по 50 шагов — это ~10 минут висящего HTTP-запроса; для
пакетов есть нативный асинхронный API. По таймауту слой возвращает 504 **вместе
с `task_ids`**, чтобы уже запущенная работа не пропала.

Конвертов ошибок намеренно два: `{"error":{code,message,request_id}}` для
`/api/v1` и `{"error":{message,type,param,code}}` для `/v1` — иначе openai-SDK
не распознаёт ошибку.

## Prompt Enhancer

Живёт в шлюзе и вызывается один раз, до диспетчеризации. Требование к эндпоинтам
одно: они не должны занимать VRAM тех карт, которые сервис и бережёт — то есть
удалённый LLM-хост или облачная модель, но не локальная. Цепочка
`IMG_PE_ENDPOINTS` пробуется по порядку; если отказали все, задача выполняется с
исходным промптом и `pe_status=failed`. Улучшение — это улучшение, а не зависимость.

Встроенный PE у ERNIE не просто выключен, а выброшен из пайплайна при
загрузке — см. примечание в разделе «Модели».

## Установка

```bash
uv sync                                    # venv шлюза (без torch)
cp .env.example .env                       # задайте IMG_API_KEYS, IMG_WORKER_TOKEN
./scripts/install_worker_into_venvs.sh     # .pth в каждый venv модели
./scripts/install_systemd.sh               # юниты и env-файлы воркеров
sudo systemctl enable --now images-worker@{qwen,zimage,ernie,hidream,qwen21,moss} images-api
```

В проектах моделей не меняется ничего, кроме одного `.pth`-файла на venv; снимается
через `./scripts/install_worker_into_venvs.sh --uninstall`.

### Подключение второго узла

```bash
# на первом узле: снять версии, отправить код и веса по LAN
./scripts/capture_venv_locks.sh
REMOTE=user@node-b MODELS="hidream zimage" ./scripts/sync_to_node.sh

# на втором узле: пересобрать venv из тех же версий
cd images-api/infra/remote-node
BACKENDS="hidream zimage" WORKER_TOKEN=<тот же, что у шлюза> ./bootstrap.sh
sudo systemctl enable --now images-worker@hidream images-worker@zimage

# обратно на первом: туннель, затем регистрация узла — без рестарта шлюза
sudo systemctl enable --now images-tunnel@node-b
curl -sS -X POST localhost:8010/api/v1/nodes -H "X-API-Key: $KEY" \
  -H 'Content-Type: application/json' -d '{
    "name":"node-b","kind":"remote",
    "base_urls":{"hidream":"http://127.0.0.1:18104","zimage":"http://127.0.0.1:18102"},
    "vram_reserve_mb":4096,"enabled":false}'
curl -sS -X POST localhost:8010/api/v1/nodes/node-b/refresh -H "X-API-Key: $KEY"
curl -sS -X PATCH localhost:8010/api/v1/nodes/node-b -H "X-API-Key: $KEY" \
  -H 'Content-Type: application/json' -d '{"enabled":true}'
```

Какие модели где лежат, шлюз выясняет из `/status` каждого воркера, поэтому
добавить модель на узел — это rsync плюс `bootstrap.sh`: без правки кода и без
рестарта. Вывести узел из работы, не потеряв текущую задачу:
`PATCH /api/v1/nodes/<name> {"draining": true}`.

`rsync -aH`, а не `tar`: кэш HuggingFace построен на симлинках и хардлинках на
blob-хранилище, rsync сохраняет это как есть и возобновляется после обрыва — на
30–60 ГБ на модель это решающее свойство.

**Про пины между версиями Python.** Лок, снятый на одной машине, не переносится,
если на целевой Python старше: мы упёрлись в `numpy==2.4.3` и `networkx==3.6.1`,
оба требуют 3.11+. Поэтому `bootstrap.sh` фиксирует жёстко только то, что
определяет поведение модели — torch, transformers, diffusers, accelerate,
tokenizers, safetensors, huggingface-hub — а остальное отдаёт pip под локальный
интерпретатор. Если жёсткий пин недоступен, скрипт откатывается в пределах
мажорной версии и печатает громкое предупреждение: молча подменять версию стека
нельзя, это меняет картинки. На нашем втором узле torch и transformers совпали
точно, разошёлся только numpy.

`flash-attn` собирается из исходников и требует torch уже в сборочном окружении,
поэтому ставится отдельно и последним. Если не соберётся — скрипт отключает его
в пайплайне HiDream, это штатный обходной путь из документации самого проекта.

## Проверки

```bash
./scripts/smoke.sh                                   # все модели сквозняком
.venv/bin/python scripts/test_exclusive_lock.py      # эксклюзив под нагрузкой
.venv/bin/python scripts/test_vram_backpressure.py   # ожидание и отказ
./scripts/test_failure_vram.sh                       # VRAM после сбоев
.venv/bin/python scripts/measure_vram.py             # калибровка пиков
.venv/bin/python -m pytest tests/ -q                 # модульные тесты
```

`test_exclusive_lock.py` проверяет, что ни один узел никогда не держит две задачи
и что общее время не ниже, чем позволяет число узлов: эксклюзив — это одна задача
на **карту**, поэтому два узла законно работают параллельно.

`test_failure_vram.sh` убивает воркер SIGKILL посреди генерации, отменяет задачу
посреди генерации и перезапускает шлюз посреди генерации, а затем проверяет, что
память вернулась и задача не потерялась молча.

## Ломающие изменения относительно отдельных сервисов

* **Плоские идентификаторы моделей.** `{"model": "turbo"}` был валиден в трёх
  сервисах с тремя разными смыслами; безопасного автоматического маппинга нет,
  поэтому возвращается 422 с перечислением кандидатов.
* **`cfg_scale` у `qwen-image` теперь действительно работает.** Старый код
  принимал параметр и не передавал его в пайплайн, тот всегда шёл на своём
  дефолте `true_cfg_scale=4.0`. Тот же seed с `cfg_scale != 4.0` теперь даёт
  другую картинку.
* **Пресет `qwen` 4:3 — 1472×1136**, а не 1472×1140: 1140 не делится на 8, и
  diffusers молча переокруглял размер.
* **API-ключ обязателен**, если сервис слушает не loopback.
* `hidream-o1` примагничивает произвольный размер к ближайшему нативному (запрос
  1024×1024 отдаёт 2048×2048). В ответе всегда фактический размер.

## Конфигурация

Всё в `.env`, образец с комментариями — `.env.example`.

| переменная | по умолчанию | что делает |
|---|---|---|
| `IMG_API_KEYS` | — | ключи через запятую, первый — админский |
| `IMG_VRAM_WAIT_TIMEOUT_S` | 600 | сколько ждать свободную карту до отказа |
| `IMG_IDLE_UNLOAD_SECONDS` | 180 | выгрузка резидентной модели после простоя узла |
| `IMG_STUCK_VRAM_SECONDS` | 300 | занятая без работы память дольше этого — инцидент |
| `IMG_ALLOW_WORKER_RESTART` | false | разрешить сторожу `systemctl restart` воркера |
| `IMG_NODES_JSON` | один локальный узел | описание узлов при первом старте |
| `IMG_PE_ENDPOINTS` | — | цепочка Prompt Enhancer, пробуется по порядку |
| `IMG_OPENAI_MAX_N` | 2 | предел `n` в OpenAI-слое |

## Требования

Python 3.12 для шлюза, 3.10+ для воркеров. Драйвер NVIDIA с `nvidia-smi`.
Ни Redis, ни брокера, ни обратного прокси — SQLite в WAL-режиме и один процесс
`--workers 1`, потому что гарантия эксклюзива держится на блокировке внутри
процесса и второй воркер uvicorn сломал бы её молча. Приложение отказывается
стартовать при `WEB_CONCURRENCY != 1`.
